# Durable official draws and portable audit records

Status: accepted for implementation.

The official draw uses SQLite with `synchronous=FULL`, a rollback journal, and explicit `BEGIN IMMEDIATE` transactions. An immutable run intent stores the exact validated snapshot bytes, input hash, method, generated seed or manual order, full priority order, and algorithm, solver, and application versions. Feasibility is established before generating a seed. The intent transaction commits before optimization starts. No pending-run API returns assignments.

Recovery acquires the writer lock before solving the persisted plan. Concurrent callers cannot compute separate results. If optimization or the final transaction fails, the intent remains pending and retains its seed and order. Recovery with different runtime versions fails closed and requires the original toolchain. A successful transaction stores the complete result and appends its commit audit event atomically. Database triggers reject changes to intent fields, committed rows, or existing audit events. Application APIs return frozen records and verify their contents against the saved snapshot and objective evaluator.

The original event key is unique. Repeating the request with a new run ID returns the same original result if snapshot and method agree; conflicting input or method fails. A restart, repeat click, preview, or repeated export cannot draw again. SQLite durability assumes a local filesystem and working storage; retain backups of the database. Hashes detect inconsistent bytes, not malicious administrators with full filesystem control.

Exceptional replacement is an explicit operation, never an automatic retry. `RunStore.replace` requires a `ReplacementAuthorization` containing a unique authorization ID, reason, approvers, and `ReplacementAuthority`. The authority explicitly supplies its policy reference, eligible administrator IDs, and required approver count. No authority or threshold is supplied by default. This records an externally adopted PTA policy; it does not claim to authenticate who supplied the policy. A replacement preserves and links the original run and output hash. Its authorization ID is unique for idempotent retries. Operators must supply the real adopted policy and authorization before live use.

The export contains `assignments.csv`, `lottery_audit.json`, `feasibility_report.json`, `lottery_summary.txt`, and exact approved input files under `snapshot/`. The canonical audit core is `CommittedRun.to_dict()`, including `schema_version: 1`, `record_type: committed_run`, `status: OPTIMAL`, and `replacement` (null for originals). `output_hash` is SHA-256 of canonical UTF-8 sorted compact JSON with final LF of this core excluding only `output_hash`. The audit adds `input_snapshot` (classes, proposals, and config) and `hash_manifest`. The manifest hashes every other exported member; it excludes the audit itself to avoid self-reference.

`verify_export` verifies member names and hashes, canonical audit bytes, core output hash, approved input hashes and schemas, embedded snapshot equality, seed/order agreement, exact CSV/report/summary consistency, all approved assignments and quotas, and the objective vector independently of the solver. Supplying an expected frozen snapshot additionally binds the export to that input. These hashes provide integrity checks, not signatures or proof of administrator identity. Proving optimization remains the solver's responsibility; regression tests compare it against exhaustive enumeration.

Exports are deterministic and never update the run. Re-export to a destination containing different bytes fails rather than overwriting unrelated results. Filesystem interruption can leave an incomplete export; verification rejects it and a repeat export repairs missing members from the unchanged committed record.

Source snapshot `approval_ids` are retained as `approvals`. Actual desktop operator signoffs are retained separately as `operator_approvals`, bound in both durable intent and audit hash. Supplied signoffs require at least two distinct IDs from the frozen source approval list. Direct API callers that omit signoffs record an empty tuple and make no claim that source-listed administrators operated the desktop. A retry cannot change previously supplied signoffs.
